## 원본 일부 조회

저장된 URL을 출력하지 않고 HTTP Range로 앞/뒤 각 64바이트만 읽었다.
두 응답 모두 206, Content-Range 전체 크기는 1,900,806,144로 요청과 같았다.
앞 8바이트를 little-endian 4 uint16로 해석한 값: [1, 0, 384, 288].
현재 파서가 사용하는 헤더 구조와 해상도는 인식 가능하다.

8바이트 헤더를 제외한 길이 1,900,806,136을 프레임당 384*288*2=221,184로
나누면 8,593프레임과 잔여 172,024바이트다. 끝부분도 바이트가 반환되었지만,
그 바이트만으로 손상/추가 메타데이터/형식 차이를 확정할 수 없다.
ATG는 39바이트 레코드 기준 18,326개다. ATT/ATG 개수 차이 자체는 별도 경고 대상이며
이번 ValueError의 직접 원인은 ATT 길이 검사다.

## 미확정 및 다음 확인

### 로컬 원본 대조 완료

사용자가 지정한 `E:/heatpipe/datasets_TB/gangseo1`에서 직접 읽기 전용으로 확인했다.
로컬 실제 파일명은 20261119_001259.att/atg로 VTI 보고의 001159와 다르지만,
ATT와 ATG 각각의 전체 SHA-256 및 크기가 서버 기록과 정확히 일치한다.

- 로컬 ATT: 1,900,806,144 bytes,
  913b65282bde4a4da03844d654ab9f15d7df5c9a570efb5c048f33ef8e5852f8.
- 로컬 ATG: 714,714 bytes,
  c3664695e656307f0ea351ab0cf10859f573ec92b88d464ba5ec688ea05f2198.
- 로컬 ATT 헤더 [1,0,384,288], 현재 파서 기준 완전 프레임 8,593개 + 잔여 172,024 bytes.

따라서 제공된 로컬 원본과 포털/워커 입력 내용은 동일하다. 이번 원인 조사에
VTI의 업로드 전 원본 크기/해시 확인을 추가 요청할 필요는 없다.
업로드 과정의 내용 변경보다는 촬영 파일 형식 또는 원본 저장 상태를 확인해야 한다.
같은 파일이라는 사실만으로 촬영 원본 손상인지 파서 가정 문제인지는 확정하지 않는다.

- 원본이 같은 경우 촬영 프로그램의 정상 저장 종료 여부와 ATT 형식 정의 확인 필요.
- 앞선 동일 파일명 검색 실패 및 원본 대조 대기 상태는 위 해시 확인으로 해소됐다.

## 조치 원칙

### 추가 조사와 처리 순서

외장하드의 다른 ATT 5개(20261026, 20261029, gangseo2, yangcheon1, yangcheon2)는
모두 같은 [1,0,384,288] 헤더이며 프레임 나눗셈 잔여가 0이었다. 문제 파일만 잔여가 있다.
문제 파일 앞 8MiB에서 같은 8바이트 헤더의 반복도 발견되지 않았다.
따라서 현재까지 전체적인 형식 변경을 뒷받침하는 근거는 없고, 개별 파일의 불완전한
복사/저장을 우선 확인한다. 해당 파일 크기는 262,144 * 7,251로 전송 블록 경계에
맞지만, 이 사실만으로 SFTP 전송 중단이라고 확정하지 않는다.

1. 촬영 장비/SFTP 저장본의 크기를 현재 외장하드 복사본과 비교한다.
2. SFTP 저장본이 더 크면 새 경로로 다시 내려받고 크기/해시/구조를 확인한 뒤 재업로드한다.
   현재 파일을 덮어쓰거나 기존 조사 자료를 삭제하지 않는다.
3. SFTP 저장본도 같은 비정렬 길이면 촬영 프로그램의 정상 종료/저장 로그와 포맷을 확인한다.
4. 불완전한 마지막 프레임만 제외하는 부분 분석은 정상 원본 확보가 불가능하고 해당
   정책이 승인된 경우에만 별도 경고/검증을 갖춰 검토한다. 현재 자동 절단은 하지 않는다.

### SFTP 저장본 크기 대조 완료

사용자가 SFTP ls -l로 다음 저장본을 확인했다.
`/upload/강서 1구간(가양대교남단_방화2/20261119_001259.att`: 1,900,806,144 bytes.
동일 폴더 ATG: 714,714 bytes. 표시된 갱신 시각은 각각 Nov 19 13:46 / 13:40.
SFTP와 외장하드의 크기는 두 파일 모두 같다. SFTP 저장본의 SHA는 아직 확인하지 않았다.
현재 SFTP 저장본보다 외장하드 복사본의 길이가 짧아진 것은 아니다.

다음 대상은 촬영 업체의 최초 저장본이다. 업체 로컬 ATT의 크기/해시 및 촬영 프로그램에서
정상 재생·저장 종료 여부를 확인한다. 업체 원본이 더 크면 SFTP 업로드 미완료 여부를
점검하고 별도 이름/임시 경로로 다시 업로드 후 검증한다. 업체 원본도 같은 비정렬
크기라면 촬영 저장 종료/파일 형식을 확인한다. 전송 중단이나 촬영 중단으로 아직 확정하지 않는다.

즉시 조치는 VTI 요청 JSON 변경이나 서비스 재시작이 아니라 올바른 입력 자료 확보다.
정상 파일 확보 후 사전 구조 검사와 전송 전후 크기/해시 대조를 통과시켜 재분석한다.

### 재발 방지 준비

- scripts/check_att_input.py: 업로드 전 8바이트 헤더, 치수, 프레임 정렬, 최소 1프레임을
  읽기 전용으로 검사한다. 위반 시 이유/파일 크기/완전 프레임/잔여 바이트 출력, 종료 코드 2.
- 이는 로컬 도구이며 포털 업로드에 아직 연결되지 않았다. 포털 사전 검사는 VTI 협의 후
  반영해야 한다. 이 도구의 PASS는 SHA/촬영 완료/모든 프레임 내용 유효성을 보증하지 않는다.
- 전송 완료 기준에 SFTP 저장본과 다운로드 복사본의 크기 대조 및 가능한 경우 SHA를 포함한다.
- worker/API 오류 분류는 현재 INVALID_ANALYSIS_REQUEST로 광범위하다. 파일 형식 오류를
  구분하는 신규 코드/상세 메시지는 VTI 계약 협의 후 별도 변경으로 준비한다.
- 운영 코드와 검증 완료 r3 이미지/manifest는 이번 조사에서 변경하지 않았다.
현재 요청 형식 변경을 요구하지 않는다. 잔여 바이트를 무조건 버리거나 프레임 수를
임의로 바꾸지 않는다. 원본과 포털 객체를 보존한다. 서비스 재시작/자동 재요청/파서 수정은
수행하지 않았다. 동일 데이터·동일 형식 오류라면 재시작만으로 해결된다고 볼 수 없다.
후속 재시험은 원인에 맞는 조치 후 새 Idempotency-Key로 요청해야 한다.
